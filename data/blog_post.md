# LLM Inference 비용 줄이는 최적화 전략

사내 LLM 서비스의 월말 청구서를 처음 열어본 날, 눈에 들어온 건 토큰 단가가 아니라 GPU가 놀고 있는 시간이었다. 모델 크기를 줄이는 쪽만 고민했는데, 실제 병목은 컨텍스트를 어디에 두고 어떻게 압축하며 어떤 순서로 스케줄하느냐에 있었다. AAAI에 올라온 컨텍스트 엔지니어링 알고리즘 논문과 alphaXiv의 RoofLang 사례를 겹쳐 놓고 보니, 실무에서 손댈 지점이 꽤 구체적으로 잡혔다.

## 1. 현장에서 무슨 일이 있었나

추론 서버를 운영하다 보면 비용은 두 갈래로 샌다. 하나는 GPU 연산 자체고, 다른 하나는 컨텍스트를 붙들고 있는 메모리다. 대화가 길어지고 문서를 통째로 밀어 넣는 요청이 늘면서 KV 캐시(어텐션 계산 결과를 재사용하려고 저장해 두는 메모리)가 차지하는 몫이 급격히 커졌다. 배치 크기를 올리면 처리량은 늘지만 첫 토큰까지 걸리는 시간이 튀고, 배치를 줄이면 지연은 잡히는데 GPU 사용률이 바닥을 친다.

AAAI 논문은 이 지점을 정면으로 다룬다. 제목 그대로 컨텍스트의 배치, 압축, 스케줄링을 하나의 최적화 문제로 묶는다. alphaXiv의 RoofLang은 한 발 더 나아가 추론 시스템 아키텍처 자체를 AI가 설계하도록 돕는 언어를 제안한다. 두 갈래 모두 모델을 바꾸지 않고 시스템을 바꾼다는 방향을 향한다.

## 2. 왜 업계가 반응하는가

모델 교체는 비싸고 느리다. 파인튜닝을 하려면 데이터와 평가 체계가 따라붙고, 배포 후 롤백 비용도 만만치 않다. 반면 서빙 레이어의 배치 정책이나 캐시 압축 방식은 설정과 코드로 바꿀 수 있다. 같은 모델로 비용을 줄이는 쪽이 조직 입장에서 훨씬 빠르다.

여기에 에이전트형 워크로드가 겹쳤다. 한 번의 질의에 검색 결과, 도구 호출 기록, 이전 대화가 전부 컨텍스트로 들어간다. 입력 토큰이 출력 토큰보다 훨씬 많아지는 구조다. 이때 컨텍스트를 얼마나 압축하고 어떤 순서로 캐시에 남기느냐가 곧 원가가 된다.

## 3. 기술적으로 보면

- **컨텍스트 배치(Placement)**: 어느 요청의 KV 캐시를 어느 GPU 메모리에 둘지 정하는 문제다. 같은 프리픽스를 공유하는 요청을 한 노드에 모으면 캐시 재사용률이 올라간다.

- **컨텍스트 압축(Compression)**: 오래된 대화나 긴 문서를 요약, 토큰 병합, 중요도 기반 절단으로 줄인다. 압축률과 정답률 사이의 타협점을 어디로 잡느냐가 설계 포인트다.

- **스케줄링(Scheduling)**: 요청을 언제 어떤 배치로 묶을지 결정한다. 연속 배칭(대기 큐를 비우지 않고 계속 채우는 방식)과 지연 상한을 지키기 위한 우선 배출이 맞물린다.

- **추론 아키텍처 생성 언어(RoofLang)**: 시스템 구성을 코드가 아니라 선언에 가깝게 기술하고, 그 위에서 AI가 배치와 자원 배분을 제안하도록 만드는 접근이다.

## 4. 실제 현장 적용 사례

프리픽스 캐싱은 이미 여러 서빙 스택에서 기본 기능으로 자리 잡았다. 시스템 프롬프트와 도구 정의처럼 매 요청 반복되는 앞부분을 캐시에 고정하면, 같은 내용을 매번 다시 계산하지 않는다. 컨텍스트 압축은 검색 증강 생성 파이프라인에서 특히 체감이 크다. 검색 결과를 그대로 붙이지 않고 순위와 중복을 정리해 넣는 것만으로 입력 토큰이 줄어든다.

RoofLang이 겨냥하는 영역은 그 위다. 사람이 손으로 튜닝하던 서빙 구성을 언어로 표현하고, 그 표현을 바탕으로 대안 아키텍처를 생성하는 흐름이다. 아직 연구 단계에 가깝지만, 배치 크기와 캐시 정책을 실험으로 찾아내는 작업을 자동화한다는 발상은 실무자 입장에서 반갑다.

## 5. 엔지니어가 봐야 할 포인트

회사에서 서빙 지표를 볼 때 가장 먼저 보는 건 평균 지연이 아니라 꼬리 지연이다. 평균은 예쁘게 나오는데 상위 구간에서 응답이 튀면 사용자는 체감으로 바로 안다. 배치를 키우는 최적화는 평균 처리량을 올리면서 꼬리 지연을 망칠 수 있으니, 두 지표를 같이 놓고 봐야 한다.

내가 보기엔 컨텍스트 압축은 정답률 회귀 테스트 없이 넣으면 안 된다. 토큰을 줄이는 건 쉽지만, 줄인 자리에 답의 근거가 사라지는 경우가 많다. 압축 정책을 바꿀 때마다 고정 평가셋으로 정답률을 다시 재는 절차를 먼저 만들어 두는 편이 낫다.

## 6. 앞으로 볼 포인트

- 배치, 압축, 스케줄링을 따로 튜닝하지 않고 하나의 최적화 문제로 푸는 접근이 실제 서빙 스택에 얼마나 빨리 내려오는지
- RoofLang 같은 아키텍처 생성 언어가 벤치마크를 넘어 운영 환경의 제약을 반영할 수 있는지
- 압축률을 올렸을 때 정답률과 꼬리 지연이 어떻게 변하는지 측정하는 표준 평가 방식이 자리 잡는지

## 7. 3줄 요약

- LLM 추론 비용의 상당 부분은 모델 연산이 아니라 컨텍스트를 붙들고 있는 메모리와 스케줄링에서 나온다.
- 컨텍스트 배치, 압축, 스케줄링을 묶어 최적화하는 연구와 아키텍처 자동 생성 도구가 같이 나오고 있다.
- 실무에서는 처리량과 꼬리 지연을 동시에 보고, 압축 정책을 바꿀 때마다 정답률 회귀 테스트를 붙여야 한다.
