# LLM 추론 최적화 핵심 기술과 배포 전략

LLM 추론 서버를 올리면서 가장 먼저 부딪히는 건 GPU 메모리 부족 알림이다. 배치 크기를 키우자니 OOM이 나고, 줄이자니 처리율이 안 나온다. 회사에서 서비스용 모델을 올리며 이 딜레마를 매일 마주한다.

## 1. 현장에서 무슨 일이 있었나

학습 단계가 끝나고 추론 서버로 넘어오면 문제가 달라진다. 학습은 파이프라인이 정해져 있지만, 추론은 요청이 불규칙하게 들어온다. GPU 여러 대에 모델을 쪼개 올리는 텐서 병렬이나 파이프라인 병렬만으로는 답이 안 나온다. 서로 다른 세대 GPU가 섞인 클러스터에서 메모리 대역폭 병목을 어떻게 풀지가 핵심 과제로 떠올랐다. 이기종 하드웨어 환경에서 메모리 병목을 완화하는 공동 설계 프레임워크가 등장한 배경이다 [출처: New Co-Design Framework Speeds Up LLM Inference on Mixed Hardware by Taming Memory Bottlenecks].

## 2. 왜 업계가 반응하는가

추론 비용이 전체 운영비의 대부분을 차지하기 때문이다. 토큰당 지연 시간을 줄이면서 동시 접속자 수를 늘려야 수익성이 맞는다. 컨텍스트 길이가 길어지면서 키-밸류 캐시(KV Cache) 크기가 선형으로 늘어나는 문제가 발등의 불이 됐다. 에이전트형 워크플로우가 일반화되면서 수십만 토큰 컨텍스트를 유지해야 하는 상황이 빈번해졌다. 컨텍스트 배치, 압축, 스케줄링을 통합 최적화하는 알고리즘 연구가 활발한 이유다 [출처: Algorithms for Context Engineering in LLM Inference: Optimization of Placement, Compression, and Scheduling]. 메모리 월을 넘지 못하면 롱컨텍스트 에이전트 서비스는 불가능에 가깝다 [출처: Combating the Memory Walls: Optimization Pathways for Long-Context Agentic LLM Inference].

## 3. 기술적으로 보면

- **KV 캐시**: 어텐션 연산에서 키와 밸류 벡터를 저장해 둔 메모리 영역. 시퀀스 길이에 비례해 증가하며 추론 단계 메모리 점유의 주범이다.
- **페이지드 어텐션(PagedAttention)**: KV 캐시를 고정 크기 블록으로 나눠 가상 메모리처럼 관리. 단편화 없이 메모리를 공유해 배치 크기를 늘린다.
- **연속 배칭(Continuous Batching)**: 요청 단위가 아닌 토큰 단위로 스케줄링. 끝난 요청 슬롯에 새 요청을 즉시 채워 GPU 활용률을 높인다.
- **추측적 디코딩(Speculative Decoding)**: 작은 드래프트 모델로 토큰을 예측하고 큰 타깃 모델로 한 번에 검증. 수용률이 높으면 지연 시간을 대폭 줄인다.
- **컨텍스트 압축(Context Compression)**: 중요도 낮은 토큰을 제거하거나 요약 벡터로 치환해 유효 컨텍스트 길이를 늘리는 기법. 배치, 압축, 스케줄링을 함께 고려해야 효과가 극대화된다 [출처: Algorithms for Context Engineering in LLM Inference: Optimization of Placement, Compression, and Scheduling].

## 4. 실제 현장 적용 사례

vLLM이나 TensorRT-LLM 같은 추론 엔진을 도입하는 건 이제 기본이다. 실무에서는 여기에 커스텀 스케줄러를 얹는다. 우선순위 높은 요청은 선점하고, 긴 컨텍스트 요청은 별도 워커로 분리한다. 양자화는 4비트까지 내려도 품질 저하가 크지 않은 구간을 찾아 적용한다. 이기종 GPU 클러스터에서는 모델 셰딩 단위를 하드웨어 메모리 대역폭에 맞춰 재조정한다. 공동 설계 프레임워크가 다루는 내용이 정확히 이 지점이다 [출처: New Co-Design Framework Speeds Up LLM Inference on Mixed Hardware by Taming Memory Bottlenecks]. 소규모 팀이라면 엔비디아 트리톤 추론 서버에 모델 레포지토리만 잘 구성해도 운영 부담이 준다.

## 5. 엔지니어가 봐야 할 포인트

내가 보기엔 프로파일링 없이 파라미터만 튜닝하는 건 삽질이다. 엔비디아 Nsight Systems나 PyTorch Profiler로 커널 단위 실행 시간을 찍어봐야 병목이 보인다. 메모리 대역폭 바운드인지, 연산 바운드인지를 먼저 가려야 한다. 실무에서 보면 배치 크기를 늘리는 것보다 KV 캐시 재사용률을 높이는 프레픽스 캐싱 효과가 더 클 때가 많다. 양자화는 정확도 지표만 보지 말고 실제 서비스 트래픽으로 A/B 테스트를 돌려야 한다. 압축 기법을 쓸 때는 검색 정확도 하락폭을 로그로 남겨 둬야 롤백 판단이 가능하다. 재미 삼아 돌려볼 만한 프로젝트 목록도 참고하면 구현 감을 잡기 좋다 [출처: 5 Fun Projects for LLM Inference Engineering].

## 6. 앞으로 볼 포인트

- 하드웨어 스펙 변화에 맞춘 컴파일러 수준 최적화가 런타임 스케줄링보다 앞서 나갈 것이다
- 롱컨텍스트 에이전트 서비스를 위한 계층적 메모리 관리 계층이 표준화될 것이다
- 추론 스택 전반을 아우르는 벤치마크 지표가 토큰당 비용 중심으로 재편될 것이다

## 7. 3줄 요약

- 추론 최적화는 메모리 대역폭과 KV 캐시 관리가 핵심 변수다
- 이기종 하드웨어 공동 설계와 컨텍스트 엔지니어링 알고리즘이 병목 해소 열쇠다
- 프로파일링 기반 병목 분석과 서비스 트래픽 검증 없는 튜닝은 무의미하다
